THE PAPER

Read the full paper

PDFAgent Assurance System (AAS)A Dual-Agent Framework for Independent Quality Assurance in AI-Assisted Software Development16 pages | NeurIPS 2026 Workshop

Abstract. AI coding assistants have dramatically accelerated software development, yet their deployment creates a structural assurance concern: when an AI agent both generates and tests its own artifacts, no independent guarantee of correctness or safety is available from that agent alone. We introduce the Agent Assurance System (AAS), a dual-agent assurance framework in which a primary Builder agent produces code and a structurally independent Assurance agent, operating alongside a human Quality Assurance (QA) engineer, provides adversarial review before any artifact enters production. AAS is organized around three independence properties (model, context, and incentive isolation) and maps onto the financial sector's Three Lines of Defence (3LoD) governance model. All empirical results are obtained on a fully synthetic benchmark of 1,200 annotated financial-software artifacts and should be read as a controlled proof-of-concept. On this benchmark, AAS reduces the critical-defect escape rate from 18.7% (same-provider self-review) to 5.1%, with roughly two-thirds of the reduction attributable to cross-provider model independence alone.

01 — THE ASSURANCE GAP

When the builder grades its own homework

AI coding agents now read requirements, write implementations, generate tests, and iterate on feedback. In regulated industries (banking, insurance, asset management) that speed arrives with a governance question: what happens when the assurance function depends on the very agent it is meant to assure?

A shared blind spot is invisible twice

If one model writes both the feature and its tests, a systematic hallucination, a category of logic error, or a security blind spot can be missed by the implementation and its verification. Prior work shows LLM-generated code introduces vulnerabilities at substantial rates, and that self-critique without external feedback has limits.

Correlated failure

A builder–reviewer pair shows correlated failure on defect category k when the reviewer's approval is positively associated with the defect being present:

What the paper claims, precisely. AAS is a proposed governance architecture, evaluated so far only on a synthetic benchmark. The contribution is a structural argument (assurance for AI-written code is a governance-architecture problem, not just a model-capability problem) plus a concrete, falsifiable instantiation others can test and replicate.
02 — DECISION PROTOCOL

One risk score, three routes

A Builder agent B produces artifact A from task T. A structurally independent Assurance agent S reviews (A, T) and emits a risk score ρ ∈ [0, 1] that decides what happens next. An Audit agent U watches the whole stream asynchronously.

The six steps

Generation

B generates A from T. First-line controls (linters, SAST, unit tests) run in parallel.

Assurance review

S computes report R with risk score ρ.

Auto-approve path (ρ < τlo)

H performs a sampled spot-check and approves if no issues are found.

Human-review path (τlo ≤ ρ < τhi)

H performs a full review of R and all critical findings.

Block path (ρ ≥ τhi)

Artifact is blocked and returned to B with R as feedback.

Escalation

Disagreements between H and S on a critical finding go to U for tie-breaking and systemic logging.

03 — THREE INDEPENDENCE PROPERTIES

What "independent" has to mean

An Assurance agent is AAS-independent of the Builder if and only if all three hold.

🧬

Model

S comes from a different model family, provider, or fine-tuning lineage than B, with no shared weights.

Removing it: 5.1% → 12.3%

🔒

Context

S's input is restricted to (A, T). No access to B's chain-of-thought, conversation history, or reasoning traces.

Removing it: 5.1% → 8.7%

🎯

Incentive

S's objective targets defect recall rather than approval rate. In practice this is a system-prompt directive, treated as a governance control.

Removing it: 5.1% → 9.4%

04 — EXPERIMENTS

What happened on the benchmark

1,200 synthetic financial-software artifacts, annotated by two blind expert reviewers each (financial-regulatory and software-security backgrounds), with senior adjudication. Cohen's κ = 0.84 overall, 0.91 for critical-severity findings. Five review conditions were compared.

How it plugs in

  • Alongside first-line controls. SAST (Semgrep, CodeQL, Snyk Code), linters and unit tests stay. S catches different classes: semantic and regulatory-intent mismatches.
  • Governance isolation in infrastructure. S's prompts, model selection and rule library are owned by risk/compliance, not the engineering manager responsible for B.
  • Audit outputs go to the CRO and audit committee, not the dev team. S's false-negative rate and category coverage are reported on a defined cadence.
  • Humans stay accountable. H is not a rubber stamp: the design focuses human attention on high-risk artifacts and contested findings.

Cost, order of magnitude

One review call over a typical artifact (≈1–5K input tokens, 0.5–2K output tokens) costs on the order of one to several US cents at 2026 frontier-model pricing. At thousands of artifacts per day that is tens to low hundreds of dollars daily for the Assurance agent. Human reviewer time on the human-review path is typically the dominant cost. These are estimates, not production data.

Hardening the Assurance agent

An adversary who controls S's prompts or rule library could silently disable the second line, which is arguably worse than an honest but weak reviewer. These mitigations are proposed, not yet implemented or evaluated:

Sign & pin

Cryptographically sign and version-pin S's system prompt and rule library; changes need risk/compliance sign-off with an immutable audit trail.

Canary artifacts

Inject artifacts with known planted defects to detect silent degradation independent of CUSUM.

Disagree-by-design

Route a small sample to a second, independently sourced Assurance agent and monitor the disagreement rate with S.

Before you adopt it

  • Builder and Assurance models come from demonstrably different providers or lineages.
  • S sees only (A, T): no builder traces, no conversation history.
  • S's prompt and rule library are owned and changed by risk/compliance, with signing.
  • Thresholds τlo / τhi calibrated on your own labelled defects, and recalibrated as the codebase drifts.
  • An Audit agent samples every path and reports outside engineering.
  • Your own cost model, and your own routing-split measurement, rather than the paper's estimates.

07 — LIMITATIONS

What this does not show

The paper states its claim narrowly: in this synthetic setting, most of the measured improvement over self-review comes from using a different model provider for review, and the extra governance machinery adds a smaller, reproducible gain on top.

  • All results are on a synthetic benchmark from a single, now-dated Builder/Assurance pair. No claim of production readiness or regulatory acceptance.
  • The cross-provider correlation coefficient ρk in Theorem 1 is introduced but never estimated, so the bound is motivating, not an empirical guarantee.
  • The conformal threshold guarantee assumes exchangeability, which real, drifting codebases violate; no validated recalibration is offered.
  • The drift-detection latency expression is an approximation, corroborated only by a low-noise simulation.
  • No SAST-augmented baseline and no same-provider baseline under varied sampling temperature.
  • Incentive independence is in practice a system prompt, not a structural guarantee; a compromised Assurance agent was not evaluated.
  • Reviewer-panel adjudication and rotation are under-documented. The benchmark, prompts and calibration code are not released with this submission.
